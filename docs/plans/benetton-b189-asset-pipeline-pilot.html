Benetton B189 Asset Pipeline Pilot

A complete asset-to-runtime validation plan for turning one Assetto Corsa car into a reusable pipeline for Overdrive's 16-car roster.

Benchmark asset: Benetton B189 Source context: Assetto Corsa KN5 → FBX Target: Unity 6000.3.19f1 / URP 17.3.0 Document date: 2026-07-31

1. Purpose

This car is the pipeline pilot. The goal is not merely to make one model look acceptable. The goal is to discover every conversion, material, hierarchy, pivot, animation, and Unity integration issue before the author delivers FBX files for the other 15 cars.

Confirmed project intent: use the Benetton as a complete test case, preserve the delivered assets, document each failure, and separate reusable pipeline work from car-specific repair.

2. System Boundaries

Source asset

KN5, converted FBX, sidecar INI, textures, LODs, empties, and source folder structure. Originals are read-only evidence.

Blender preparation

Correct materials, alpha behavior, normal maps, body response, pivots, offsets, hierarchy, and export readiness.

Unity integration

Import settings, URP materials, prefab hierarchy, animation hooks, camera compatibility, colliders, LODs, and runtime control.

Play Mode validation

Render and drive the car in the actual game context. Verify steering, wheel rotation, cockpit/chase presentation, lighting, and performance.

Important boundary: Blender can validate static asset correctness and prepare pivots. Unity must implement runtime steering, wheel rotation, physics linkage, and presentation-state behavior.

6. Wheel and Steering Validation

Static Blender checks

  • Each front wheel root must be centered on the steering pivot.
  • Left/right wheel roots must be mirrored on the lateral axis.
  • Disk, rim, tire, and brake components must share the intended wheel center.
  • Front-wheel steering rotation must occur around the vertical steering axis, not the tire axle.
  • Wheel offsets must be compared as mirrored values, not copied with the same sign.

Unity runtime checks

  • Front wheels steer with the visual steering value.
  • All wheel assemblies roll with vehicle travel.
  • Steering and rolling rotations do not overwrite each other.
  • Wheel visuals remain aligned with physics/collider positions.
  • Wheel animation remains correct in cockpit and chase cameras.
Architecture implication: the imported WHEEL_LF and WHEEL_RF empties are suitable candidates for steering pivots, but the final runtime contract belongs in Unity and must be tested against the vehicle-physics presentation state.

6A. Next Execution Stage: Blender Pilot Consolidation

Stage 1 consolidates the confirmed Blender repairs before any Unity import. It intentionally keeps the car and pilot as separate runtime domains.

Car-owned visuals

STEER_HR, dashboard meshes, wheels, suspension groups, bodywork, materials, and car animation pivots remain part of the car prefab.

Pilot-owned visuals

The pilot mesh, skeleton, hands, arms, and DRIVER:RIG_* animation targets remain a separate reusable prefab.

Shared runtime state

Steering angle, speed, RPM, gear, and suspension presentation are published by the vehicle and consumed by cockpit and pilot presentation controllers.

Animation bridge

The KSANIM parser produces transform data first. A later adapter maps those targets to a pilot rig or to car-owned cockpit objects.

Correct driver found

DRIVE_BASE.fbx was found in the 1989 asset root and imports with the complete driver, helmet, visor, and 55-bone DRIVER:* armature. Materials and cockpit alignment still require preparation.

The package also contains twelve decoded external animation clips covering suspension arms, hubs, wheels, blur rims, driver steering, gear shifts, helmet/body motion, and rain effects. Full clip classification is recorded in docs/plans/benetton-b189-animation-inventory.md.

Measured keyframes show that hubs and suspension arms carry suspension motion, while wheel, tire, rim, blur-rim, and rear-transmission targets are static in the sampled clips. These latter behaviors should be owned by runtime visual controllers unless later parent-space analysis proves otherwise.

The final DRIVE_BASE.fbx test succeeded: the imported driver includes helmet geometry, visor geometry, the expected DRIVER:* armature, relinked Benetton materials, cockpit alignment, and a tested 121-frame Action.

The isolated completeness audit confirmed the driver mesh is complete. The cockpit render hides the torso and legs through normal geometry occlusion; the final player-camera cockpit view remains the presentation check.

The Steam Editor package did not contain the driver, but the exact file was found in the supplied F1 1989 asset root.

9. Acceptance Criteria for the Pilot

  1. Original source files remain byte-identical and are never overwritten.
  2. Every Blender repair has a before/after screenshot and a saved output path.
  3. All four wheels have verified centers, mirrored offsets, and correct component hierarchy.
  4. Front-wheel steering can be previewed with the correct pivot before Unity import.
  5. Unity imports the prepared car without missing references or console errors.
  6. Play Mode renders the car under Overdrive lighting without metallic/mirror-like body response.
  7. Front wheels steer and all wheels roll in runtime.
  8. Cockpit and chase views both remain readable at racing speed.
  9. The final report separates reusable pipeline fixes from Benetton-specific exceptions.

10. Non-Goals

  • Reproducing Assetto Corsa's original shader feel.
  • Preserving every Assetto-specific material channel when it conflicts with Overdrive's visual direction.
  • Using this one car to assume every author-supplied FBX has the same hierarchy.
  • Declaring the pipeline complete before the Unity Play Mode test passes.
