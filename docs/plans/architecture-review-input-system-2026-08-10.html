Ordering is documented, never enforced. Every test re-writes the 4-call sequence by hand.

After — one deep module owns the sequence

flowchart TD
  D[InputFrameDriver] --> R[ResolveActiveScheme]
  D --> C[CaptureLatestRawSample]
  D --> T[TickProcessor]
  D --> E[ConsumePendingPauseEdge]

  style D fill:#0f172a,color:#fff
  style R,C,T,E fill:#e2e8f0,stroke:#94a3b8

One Step() entry point; ordering becomes structural, not documentary.

Problem. The system's real behavior — a 4-call ordered sequence plus a 3-step pause-edge handshake — exists only in doc comments and re-implemented per test, because the production caller (Simulation driver) is not built yet.

Solution. One per-frame module that owns resolve → capture → tick → edge consumption behind a single entry point; the controller provides raw samples and scheme decisions, the processor stays pure.

  • locality: the protocol concentrates in one module
  • leverage: one interface, N future call sites
  • ADR-0001 ordering becomes structural, not a comment
  • tests hit one seam instead of re-building the driver

  • Settings-vs-runtime drift risk disappears
  • preview and future driver stop re-spelling the mapping

Top recommendation

Start with 1. Encapsulate the per-frame input protocol — it is the largest friction source. The pure pipeline modules are already deep and well-tested; the system's real behavior (the 4-call ordered sequence + pause-edge handshake) exists only in comments and per-test mocks, and the production caller is built in the next epic. Wrapping it now turns ADR-0001's ordering constraint from documentary into structural, and gives the Simulation Kernel a contract to consume instead of a sequence to re-implement by hand.

Execute in order: 2 (single tuning owner) and 3 (collapse pause-edge) first — they clear the base the driver would otherwise inherit. Then 1.
