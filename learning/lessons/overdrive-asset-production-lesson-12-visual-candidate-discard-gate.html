Overdrive Asset Production · Technical candidate evaluation

How to evaluate a downloaded car as a game asset

11-point audit · Blender + Unity · ~60 min per candidate · Mission: MISSION.md

The question this lesson answers

All candidates in the current inventory have already passed the visual selection made before this audit: they are attractive Formula cars from the target period. The question here is different:

Which visually acceptable model is technically the best base for the Overdrive car pipeline?

This lesson does not teach how to recognize an F1 car. It teaches how to inspect a model's data, organization, runtime cost, and production dependencies before choosing it for a first test.

What a “good” candidate means in this project

A good first-test candidate is not necessarily the most detailed, the most expensive, or the most historically famous model. It is the model that lets us test the pipeline without an unrelated technical failure obscuring the result.

For this project, the candidate must eventually support:

  • one exterior car asset: bodywork, cockpit surround, wings, wheels, and suspension;
  • a shared internal cockpit module: driver, seat, belts, steering wheel, dashboard, and pedals;
  • Unity material replacement and Overdrive livery work;
  • wheel and vehicle presentation animation;
  • up to 16 car instances in a race scene;
  • Addressables loading and a reusable car prefab.

The audit separates hard blockers from preparation work. A missing LOD or collider may be work we can add. A legally unusable model or a failed import route may block the candidate entirely.

Tool capability audit

No new tool is required for the first audit. The connected Blender MCP can inspect the scene directly and can execute Blender Python when a built-in information panel is insufficient. Unity MCP can verify the imported asset after the Blender stage.

Important: a tool can report that Blender opened a file. That is only the first format check. It does not prove that the complete production route works.

Before starting: create a diagnostic copy

Do not evaluate by modifying the only copy of a downloaded model.

  1. Keep the downloaded source untouched.
  2. Open or import the candidate into Blender.
  3. Use File → Save As.
  4. Use a diagnostic name such as candidate-march-cg891-technical-audit.blend.
  5. Do not apply transforms, delete objects, join meshes, or repair holes during the audit.

The purpose of the first pass is to measure and understand the candidate. Editing before recording the original state hides the cost of preparation.

1. Format and import route

What it is

A format is not only the file extension. It is the way the file stores meshes, hierarchy, materials, textures, animation, and external dependencies.

The current folder includes formats such as:

  • GLB/GLTF: a packaged exchange format that often carries meshes, materials, textures, and sometimes animation in one file;
  • FBX: a broad exchange format commonly used for Unity, but material and animation interpretation depends on export settings;
  • KN5: an Assetto Corsa-oriented format. Opening or converting it does not automatically preserve a clean general-purpose production structure;
  • DAE and converted files: alternative exchange copies whose data may differ from the original.

Why “it opens in Blender” is not enough

Blender opening the file proves only that the current Blender installation has a reader or importer for that file. The production question is:

Can this candidate travel from its source representation to Blender, then to Unity, while preserving the data we need?

A file may open while losing:

  • material assignments;
  • texture paths;
  • object hierarchy;
  • animation actions;
  • custom properties;
  • correct scale or axis orientation.

Where and how to verify

  1. Record the original filename and extension.
  2. Record whether the model was imported directly or converted from another format.
  3. In Blender, inspect the Outliner, materials, textures, actions, and transforms before exporting.
  4. Export a diagnostic FBX or GLB using a deliberate export scope.
  5. Import that diagnostic export into Unity.
  6. Compare the Blender source and Unity result: object count, mesh appearance, materials, textures, scale, orientation, and animation.

Pass, warning, and blocker

StatusMeaning
PassThe candidate survives a documented Blender-to-Unity round trip with the required data intact.
WarningThe candidate opens, but conversion or export loses fixable data such as material links or animation clips.
BlockerThe candidate cannot be exported/imported reliably, depends on an unavailable proprietary route, or loses essential geometry or structure.

MCP capability: Blender MCP can inspect the imported scene and execute a round-trip audit. Unity MCP can verify the destination asset. The license and proprietary-converter question require external source research; no editor tool can answer them.

2. Hierarchy and object separation

What hierarchy means

Hierarchy is the tree of objects and parent-child relationships inside the model. It is not the same as visual appearance and not the same as material slots.

Car_Root
├── Body
├── Cockpit_Surround
├── FrontWing
├── RearWing
├── Wheel_FL
├── Wheel_FR
├── Wheel_RL
├── Wheel_RR
└── Suspension

A model can look perfectly assembled while being one single mesh object. That may be acceptable for a static render, but it makes wheel rotation, suspension animation, material replacement, part replacement, and cockpit insertion harder.

Where to inspect

  1. Open the Outliner.
  2. Expand the car collection.
  3. Count the mesh objects and identify their names.
  4. Select a wheel and move only the selection temporarily in the diagnostic copy; undo immediately.
  5. Confirm whether the wheel is a separate object or only a disconnected island inside the body mesh.
  6. Inspect parent arrows and indentation in the Outliner.

For a non-destructive audit, Blender MCP can perform the same check through bpy.data.objects and report object type, parent, collection, vertex count, and bounding box without moving anything.

Pass, warning, and blocker

StatusExampleProduction meaning
PassBody, wheels, wings, suspension, and cockpit surround are independently addressable.Good base for assembly and later animation.
WarningSome parts are fused but can be separated with a controlled cleanup operation.Preparation cost must be estimated before choosing the candidate.
BlockerEssential moving or replaceable parts are fused into a dense mesh and separating them would require destructive remodeling.Poor first-test candidate.

MCP capability: fully inspectable through Blender MCP, especially with a short bpy audit. A screenshot alone is not sufficient because it cannot show whether two visible parts are separate objects.

3. Scale, orientation, and pivots

Definitions

  • Scale: the physical size of the model and the scale values applied to its objects.
  • Orientation: which direction is forward, which axis is vertical, and how the model is rotated relative to the game.
  • Pivot/origin: the point around which an object rotates, scales, or is positioned.

Why they matter

Scale affects physics, camera distance, lighting, collision size, and the relative position of the shared cockpit. Orientation affects movement direction, camera placement, export conventions, and prefab setup. Pivots affect animation.

A wheel can look correct while having its origin several centimeters away from its axle. In Unity, rotating that wheel around the wrong origin makes it orbit or wobble instead of rolling.

Where to inspect

  1. Select the car root and open N → Item.
  2. Record location, rotation, scale, and dimensions.
  3. Select each wheel and record its origin relative to the wheel center.
  4. Enable the object-origin display if necessary.
  5. Use the same axis convention for every candidate and record any conversion needed.
  6. Do not apply transforms during the audit; record the current state first.

Blender MCP can inspect object transforms, world-space matrices, dimensions, and origins through bpy. A viewport screenshot can prove the visible axis relationship but not replace the numeric record.

Pass, warning, and blocker

  • Pass: one consistent car scale, known forward/up axes, and wheel origins near axle centers.
  • Warning: scale or orientation needs a documented normalization step.
  • Blocker: parts use inconsistent scales, wheel pivots are unusable, or the model cannot be normalized without changing geometry relationships.

4. Triangle count and mesh cost

What is being counted?

A mesh may be described by vertices, edges, faces, or triangles. The renderer ultimately processes triangles, so the audit records triangles rather than relying only on the number of polygons shown in Blender.

  • Vertex: a point in space.
  • Edge: a connection between points.
  • Face/polygon: a surface region, often a quad or triangle.
  • Triangle: the basic primitive used by the renderer after triangulation.

Where to see it in Blender

  1. Open Viewport Overlays.
  2. Enable Statistics.
  3. Read the viewport statistics for selected objects and the scene.
  4. For an exact audit, use Blender MCP Python to call mesh.calc_loop_triangles() and count mesh.loop_triangles.
  5. Record LOD0 total triangles and the largest individual objects.

The exact number must be recorded from the candidate rather than guessed from its appearance. The project loads 16 car slots, so also record the simple projection:

LOD0 triangles × 16 cars

This is not the final frame-cost prediction because materials, LOD selection, shadows, culling, and screen size also matter. It is a first risk indicator.

Do not invent a pass threshold

No approved project-wide triangle budget is established by this audit. Therefore, do not call a 50,000-triangle model automatically good or a 100,000-triangle model automatically bad. Compare the candidates, inspect their LODs, and measure the actual Unity scene before setting a production budget.

Pass, warning, and blocker

  • Pass: the cost is known, the mesh is not obviously wasteful, and reduction or LOD creation is practical.
  • Warning: the candidate is heavy but has useful detail, or no LOD exists yet.
  • Blocker: the candidate is so heavy or fragmented that it prevents a controlled first Unity test and cannot be reduced without destroying the required form.

MCP capability: fully measurable via Blender Python. Unity profiling is still required for the final runtime decision.

5. UV maps

What a UV map is

A UV map is the two-dimensional layout that tells a texture where to appear on a three-dimensional mesh. The letters U and V represent the texture-space axes, separate from the model's X, Y, and Z axes.

Where to inspect

  1. Select a body mesh.
  2. Open the UV Editing workspace.
  3. Check the Object Data Properties → UV Maps list.
  4. Enter Edit Mode and select all faces.
  5. Confirm that the UV islands appear in the UV Editor.
  6. Inspect body, wings, wheels, cockpit, and suspension separately.
  7. Check whether unique left/right markings require overlapping UVs or have distinct islands.

Blender MCP can report the existence and names of UV layers and can calculate basic UV coverage. It can also generate diagnostic screenshots. Exact quality still requires looking at the UV layout because a UV layer can exist while being unusable.

Reproducible UV-space and overlap check

The following is the exact verification protocol used on the March CG891 in Blender 5.2.0 LTS. It distinguishes a UV layout that looks organized from one that gives important livery surfaces enough texture resolution.

  1. Work in the UV Editing workspace. In the tested Blender 5.2 layout, the large area on the left was an Image Editor/UV Editor and the 3D Viewport was on the right. The location can vary, so always place the mouse over the intended area before using a shortcut.
  2. In the 3D Viewport, enter Edit Mode and select the body faces to measure: first the engine-cover side, then the main sidepod livery panel.
  3. Move the mouse over the UV Editor and press Alt+A before making a new selection. This clears the previous UV-overlap selection.
  4. Observe the selected UV region. The full UV tile represents coordinates 0–1. On the observed grid, each major division is approximately 0.1 UV units.
  5. For a 2048×2048 texture, convert normalized UV size to pixels with:
    pixel width = UV width × 2048
    pixel height = UV height × 2048

Blender 5.2 does not provide a simple Width/Height readout for a multi-face UV selection in the standard UV Editor sidebar. The grid is sufficient for a quick visual estimate. For an exact, non-destructive measurement, use the MCP tool blender-mcp_execute_blender_code with this Blender Python audit:

import bpy, bmesh, json

obj = bpy.data.objects.get("march")
bm = bmesh.from_edit_mesh(obj.data)
uv = bm.loops.layers.uv.active

points = []
selected_faces = 0
for face in bm.faces:
    if face.select:
        selected_faces += 1
        points += [(loop[uv].uv.x, loop[uv].uv.y) for loop in face.loops]

unique_points = []
for point in points:
    if not any(abs(point[0] - other[0]) < 1e-6 and
               abs(point[1] - other[1]) < 1e-6
               for other in unique_points):
        unique_points.append(point)

min_x = min(point[0] for point in unique_points)
max_x = max(point[0] for point in unique_points)
min_y = min(point[1] for point in unique_points)
max_y = max(point[1] for point in unique_points)

print(json.dumps({
    "selected_faces": selected_faces,
    "uv_width": max_x - min_x,
    "uv_height": max_y - min_y,
    "pixel_width_at_2048": (max_x - min_x) * 2048,
    "pixel_height_at_2048": (max_y - min_y) * 2048
}, indent=2))

The result is a bounding-box measurement, not the exact filled area of the island. It is still the correct first metric for checking whether a livery panel is too small for readable markings.

March CG891 evidence: the selected engine-cover side measured approximately 0.12055 × 0.28916, or 247 × 592 pixels at 2048×2048. The selected sidepod measured approximately 0.17670 × 0.35700, or 362 × 731 pixels. The sidepod is therefore the stronger livery surface and is large enough for a number, stripe, and medium-sized sponsor treatment.

UV-overlap check

  1. With the UV Editor active, press A.
  2. Press F3 and search for Select Overlap.
  3. Press Enter. Do not move or delete the selected UVs.
  4. Inspect the corresponding orange faces in the 3D Viewport.

Overlapping UVs are acceptable on surfaces that intentionally share one uniform or seamless texture. They are a warning when those faces may later receive different numbers, logos, damage, or directional markings. They are a blocker on a lightmap UV channel that must remain unique for baked lighting. Always record which UV channel was tested; the March livery check used UVChannel_1 and the body texture march_16extra0.dds at 2048×2048.

Pass, warning, and blocker

  • Pass: important visible meshes have usable UVs and there is enough layout for the intended livery.
  • Warning: UVs exist but are crowded, mirrored, stretched, or require repacking.
  • Blocker: the body has no usable UVs and the intended surface workflow depends on painted livery that cannot be applied without a full unwrap.

Mirrored UVs are not automatically bad. They are only a problem when the left and right sides need different readable markings.

6. Materials and textures

What to inspect

A material is the set of surface parameters assigned to a renderer. A texture is an image or data map used by that material. A shader is the program that interprets those inputs.

Inspect:

  • material slots per renderer;
  • total material count;
  • base-color textures;
  • normal, roughness, metallic, and emission maps;
  • missing image paths;
  • shader names and custom nodes;
  • whether materials are shared across unrelated parts.

Where to inspect

  1. Select an object and open Material Properties.
  2. Record every material slot.
  3. Open the Shader Editor.
  4. Trace image texture nodes and note their file paths.
  5. Use File → External Data → Report Missing Files when appropriate.
  6. Use Blender MCP Python to produce a complete material-to-object and material-to-texture report.
  7. After Unity import, inspect the generated materials and shader assignments with Unity tools.

Pass, warning, and blocker

  • Pass: materials and textures are discoverable, replaceable, and can be routed to the project's URP material strategy.
  • Warning: many materials, missing textures, or game-specific shader graphs require consolidation.
  • Blocker: essential visual data is inaccessible, encrypted, legally unusable, or dependent on a shader that cannot be reproduced in Unity.

The original livery does not need to be retained. The technical question is whether the model provides a workable surface representation or a clean mesh that can receive new materials.

Blender 5.2 practical procedure

  1. Select the object in the 3D Viewport or Outliner.
  2. Open Material Properties in the Properties editor. The icon is the red sphere near the bottom of the vertical icon strip.
  3. Record the material slots assigned to that object.
  4. Switch to the Shading workspace. The Shader Editor is normally along the bottom of the workspace.
  5. Find the Image Texture, Principled BSDF, and Material Output nodes.
  6. Confirm that image Color connects to Base Color and that the normal texture passes through Normal Map into Normal.
  7. Inspect whether an image Alpha socket is connected to Principled BSDF → Alpha. Disconnect the wire by dragging from the socket into empty space only when the surface is opaque.
  8. For Assetto Corsa atlas materials, Alpha is often a shader mask, not transparency. This was proven on the March bodywork, carbon floor, dashboard, and steering-wheel materials.
  9. Keep Alpha for genuine glass, glow, LED, blur, or cutout materials until their visual result is confirmed.
  10. Run File → External Data → Report Missing Files.
  11. Inspect the final result in Material Preview from front, rear, side, top, and three-quarter views.

Worked material example: March CG891

The March audit found 42 materials, 33 textures, and no missing texture references. The original Assetto Corsa Alpha connections made opaque body and cockpit geometry invisible in Blender. Removing only the incorrect Alpha-to-Alpha connections revealed the existing carbon floor, cockpit panels, dashboard, steering wheel, buttons, and gear lever. No replacement geometry was required.

The correct result is PASS with engine-conversion work remaining: the source materials are discoverable and usable, while Unity/URP materials will be created later. Do not remove Alpha from every material without checking whether it represents real glass, glow, or cutout behavior.

7. Animations and rig data

What to inspect

Inspect whether the candidate contains:

  • armatures and bones;
  • object actions;
  • shape keys;
  • wheel rotation actions;
  • steering actions;
  • suspension actions;
  • driver actions;
  • duplicate or validation clips.

Where to inspect

  1. Check the Outliner for armatures.
  2. Open the Dope Sheet → Action Editor.
  3. Open the NLA Editor if the candidate uses NLA tracks.
  4. Check Blender's bpy.data.actions through MCP Python.
  5. Record action names, frame ranges, and the objects they animate.
  6. Verify whether animation data is part of the car or belongs to a separate driver.

Interpretation

No animation is not automatically a failure. A static car with clean wheel objects and correct pivots can receive animation later. Conversely, hundreds of imported clips are not automatically valuable; they may be validation actions from the source game.

  • Pass: animation ownership is understandable, or the model is cleanly static and ready for our own animation setup.
  • Warning: useful parts exist but actions require cleanup or rebaking.
  • Blocker: essential parts depend on a broken rig or animation data that cannot be separated from the asset without losing the car.

MCP capability: Blender MCP Python can inspect actions, F-curves, armatures, constraints, and object animation. Actual motion quality still requires playing or rendering the animation.

Blender 5.2 practical procedure

  1. In the Outliner, search for Armature. Record whether an armature exists.
  2. Change an editor to Dope Sheet using the editor-type button at the top-left of that editor.
  3. In the Dope Sheet mode selector, choose Action Editor. Record the available actions and frame ranges.
  4. If the asset uses animation tracks, change an editor to NLA Editor and record its tracks.
  5. Select a mesh, open Object Data Properties (green triangle icon), and inspect the Shape Keys panel.
  6. In the Outliner, expand the wheel groups and record whether the tyre, rim, disc, and blur parts are separated and parented together.
  7. Enable origin display in the 3D Viewport: click the small arrow beside Overlays (the two overlapping circles), open Objects, then enable Origins or Origins (All).
  8. Do not move origins during the evaluation. An origin at world 0,0,0 is evidence that the part still needs a functional pivot; it is not a reason to move the mesh itself.

Wheel animation interpretation

Separate wheel parts are valuable, but separation alone is not a pivot. The complete wheel assembly must rotate together around a new pivot at the axle center:

STEER_LF
└── ROLL_LF
    ├── Tyre
    ├── Rim
    ├── Disc
    └── Blur

STEER_LF turns a front wheel left or right. ROLL_LF rotates the complete assembly while the car moves. Rear wheels normally need only the rolling pivot. A wheel-side mesh separated from the centre is useful because it reduces editing work, but the tyre, rim, disc, and blur meshes must still be placed under the same rolling pivot.

Worked animation example: March CG891

The March contains no armature, no Actions, and no Shape Keys. It does contain four wheel groups (WHEEL_LF, WHEEL_RF, WHEEL_LR, and WHEEL_RR) with separated disc, rim, tyre, and blur branches. The groups are useful organization, but the audited origins are all at world 0,0,0; they are not functional wheel pivots yet.

Classification: WARNING, not BLOCKER. This is a clean static source that can receive steering and rolling pivots later. No imported animation is required for the model to become a usable game asset.

8. LODs

What LOD means

LOD means Level of Detail. A model has multiple visual versions, and the game selects a cheaper version when the car is farther from the camera.

Where to inspect

  1. Search the Outliner for names such as LOD0, LOD1, LOD2, or source-specific equivalents.
  2. Compare each variant's triangle count with the high-detail version.
  3. Compare the silhouette and important parts between variants.
  4. Check for missing wheels, wings, or materials in the lower variants.
  5. After Unity import, verify whether a real LODGroup can be created and configured.

Blender MCP can identify candidate LOD objects, compare their mesh statistics, and report whether they are genuinely different meshes. Unity MCP can verify the runtime LODGroup after assembly.

  • Pass: existing LODs are real, progressively cheaper, and visually stable.
  • Warning: LODs are absent or need creation, but LOD0 is usable.
  • Blocker: lower variants are broken, misleadingly named, or the LOD structure cannot be separated from unrelated source-game logic.

9. Colliders

What a collider is

A collider is the simplified physical shape used for contact and physics queries. It is not the same as the detailed visible mesh.

Typical car colliders include:

  • body/chassis collider;
  • wheel colliders or wheel reference objects;
  • front and rear collision volumes;
  • source-game helper meshes.

Where to inspect

  1. In Blender, inspect the Outliner for objects named COL, Collider, or similar.
  2. Check whether helper meshes are visibly separate from render meshes.
  3. After Unity import, inspect GameObject components with Unity's component tools.
  4. Record whether the collider is a usable primitive, a mesh collider, or merely source-game data.

Blender MCP can report helper objects and mesh statistics. Unity is the authoritative place to verify Collider components and their settings.

  • Pass: collision can be created or reused without coupling it to the render mesh.
  • Warning: no usable collider is included, but the car body can receive a new simplified collider.
  • Blocker: the candidate depends on inaccessible source-game collision logic or the render hierarchy makes a safe collision setup impractical.

A missing collider alone should not reject an otherwise excellent visual model. It is normally preparation work.

10. Shared cockpit integration

Project-specific boundary

Each car owns its exterior: bodywork, cockpit surround, wings, wheels, suspension, and livery. The project uses one shared internal cockpit containing the driver, seat, belts, steering wheel, dashboard, and pedals.

The audit therefore does not ask whether every downloaded car has a complete historical interior. It asks whether the car's exterior can accept the shared module.

Where to inspect

  1. Hide the driver and interior objects in the diagnostic copy.
  2. Inspect the external cockpit opening from side, front three-quarter, rear three-quarter, and top views.
  3. Check whether the opening is a clean boundary in the exterior shell.
  4. Measure the opening and record its center, width, length, and height.
  5. Check whether bodywork blocks the planned driver, steering wheel, or dashboard volume.
  6. Check whether the internal cockpit is fused to the exterior mesh.

Blender MCP can inspect the object boundary, bounding boxes, and separation. A screenshot is required to prove the visual fit; numeric dimensions alone do not prove that the module will look correct.

  • Pass: the exterior opening is usable and the internal cockpit can be replaced or inserted.
  • Warning: interior removal or a small fit adjustment is required.
  • Blocker: the exterior has no usable cockpit boundary or the cockpit is fused into essential bodywork in a way that requires remodeling.

11. License and provenance

Why it belongs in the technical audit

A model can be technically excellent and still be unusable in a commercial or public game. Download location alone does not establish rights.

What to record

  • source website and product page;
  • creator or publisher;
  • license text;
  • commercial-use permission;
  • permission to modify;
  • permission to redistribute inside a compiled game;
  • texture and material license;
  • whether the model was extracted from another game;
  • purchase receipt or account record, if applicable.

Neither Blender MCP nor Unity MCP can prove this. This criterion requires reading the source license and, when necessary, contacting the creator. A missing license is a production risk, not evidence that the mesh is bad.

  • Pass: rights cover the intended use.
  • Warning: rights are unclear and require confirmation.
  • Blocker: the license prohibits the intended use or the model is clearly extracted without redistribution permission.

Recommended audit order

Do not spend equal time on every criterion before checking the likely blockers. Use this order for each candidate:

  1. source and license;
  2. format route and diagnostic round trip;
  3. hierarchy and object separation;
  4. scale, orientation, and wheel pivots;
  5. triangle count and mesh cost;
  6. UV maps;
  7. materials and textures;
  8. cockpit boundary;
  9. animations;
  10. LODs;
  11. colliders.

If a candidate fails a hard blocker in the first three stages, record the reason and stop spending time on the remaining stages. If it passes, complete the full audit so candidates can be compared fairly.

What this audit proves

At the end of the audit, the decision must be evidence-based:

  • not “this model looks good”;
  • not “Blender opened it”;
  • not “it has many polygons”;
  • not “it already has textures”.

The useful conclusion is:

This candidate has a known import route, separable production parts,
correct transforms and pivots, usable UV/material data, a measurable
mesh cost, a compatible cockpit boundary, and no unresolved blocker.

Only then is it a defensible first model for the Overdrive pipeline.
