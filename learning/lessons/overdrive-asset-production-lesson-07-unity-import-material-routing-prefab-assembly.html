Overdrive Asset Production · Lesson 7

Unity import, material routing, and prefab assembly

2026-08-07 · Mission: MISSION.md · ~50 min

The question this lesson answers

When an FBX enters Unity, what exactly is created, which material does each renderer use, and when is the imported model ready to become a reusable production asset?

An imported model is not a single object. It is a routed group of meshes, materials, textures, shaders, animation clips, and scene instances.

This lesson follows the real Ferrari import. The car appeared visually correct in some places, but its material source, shader, texture transform, embedded subassets, and external material copies were not the same thing. Understanding those routes prevents a material change on one car from silently changing another.

1. The import chain

The useful mental model is:

FBX file
  ↓ Model Importer
imported model prefab + subassets
  ↓ scene instance
GameObjects with MeshFilters and MeshRenderers
  ↓ material slots
Material
  ↓ shader properties
Shader + textures + surface settings
  ↓ rendering
visible object

The FBX is the source container. The visible car is produced by the complete chain, not by the filename alone.

2. One FBX becomes several Unity assets

When a model contains meshes, materials, textures, and animation data, Unity imports them as a group of assets and subassets. The main Project item may appear as a model prefab, while its meshes, materials, and AnimationClips are nested under the same imported file.

This creates three different things that must not be confused:

ItemMeaningCan it be deleted independently?
FBX source assetThe imported model container and importer settingsYes, as the main Project asset
Embedded material subassetA material generated inside the imported modelNot as an independent production material
Scene model instanceA placed copy of the imported model prefabYes; this removes only the scene instance

Selecting a child such as fer_coverengine-1 selects a scene GameObject. Selecting WCCARBODY under the FBX selects an embedded material subasset. Selecting the .fbx file in the Project window selects the importer and the main asset. These selections expose different controls.

3. Read the Model Importer before changing anything

Select the FBX file itself in the Project window. The Import Settings inspector exposes tabs such as:

  • Model: geometry, hierarchy, normals, tangents, visibility, and mesh options;
  • Rig: skeleton and avatar interpretation;
  • Animation: imported clips and action ranges;
  • Materials: material creation, location, naming, search, and texture extraction.

Importer settings apply to that model asset. They are not the same as editing one renderer in the scene. Do not change Model settings to solve a material-routing problem, and do not change a shader to solve missing geometry.

4. Embedded materials versus external materials

The Materials tab controls where Unity stores or resolves imported materials. The labels can vary slightly by Unity version, but the two important concepts are:

RouteResultConsequence
Embedded / In PrefabMaterials remain inside the imported modelConvenient for a quick import; Inspector editing is limited
ExternalMaterials are extracted or resolved as separate .mat assetsThey can be edited in the Inspector and reused by other renderers

Unity's external-material route searches for existing material names before creating new ones. If a Materials folder already contains a material with the same name, Unity can resolve the existing asset instead of creating an isolated copy. This is why material search and folder structure are production decisions, not cosmetic settings.

The Ferrari routing failure

When the second Ferrari was changed to external materials, Unity resolved material names that already belonged to the first Ferrari. Both scene cars then appeared to use the same materials and the same shader treatment. The problem was not that Simple Lit or Unlit had merged. The problem was that both renderers pointed to the same material assets.

The correct separation is:

First Ferrari
  → original external materials

Second Ferrari
  → uniquely named or uniquely extracted material copies
  → separate shader and surface experiments

For an isolated experiment, extract or create the second car's materials in a dedicated folder such as Materials_SecondCar. Then inspect the renderer's material slot and confirm that it points to the new asset, not merely to a material with a similar name.

5. Material routing is visible in the renderer

To trace a visible surface, follow this order:

GameObject
  → MeshRenderer
  → material slot
  → .mat asset or embedded material
  → Shader
  → Base Map and other texture slots
  → visible result

For the Ferrari, a renderer such as fer_body-6 routes through a material and then to the decal texture. The tire renderers use separate left and right sidewall materials. A change is meaningful only after the complete route is recorded.

Use a copied external material for an A/B experiment. Editing a shared material changes every renderer that references it, including other scene instances and other cars that resolve the same asset.

6. Why embedded material fields can be grey

An embedded material belongs to the imported FBX. It is not an ordinary standalone .mat file. The Inspector may display its shader and properties while preventing normal asset editing.

The Editor workflow is:

  1. select the .fbx file in the Project window;
  2. open the Materials tab of the Model Importer;
  3. use the extraction control or external-material location;
  4. choose a dedicated folder when the experiment must not share materials;
  5. select the resulting .mat file in the Project window;
  6. edit the Shader, Base Map, Normal Map, Smoothness, and other properties.

Do not treat a grey Inspector field as evidence that the material is broken. It usually means that the selected object is an embedded imported subasset rather than an external material asset.

7. Shader changes have a reference scope

Changing the Shader field on an external material changes the material asset itself. Every renderer using that asset receives the change.

Change targetScopeSafe use
Imported embedded materialModel import result; may be regenerated on reimportShort-lived inspection
Shared external materialEvery renderer referencing the materialIntentional shared style
Copied external materialOnly renderers assigned to the copyA/B comparison and isolated restyling
Renderer material overrideOne scene instance or rendererTemporary scene experiment

The Ferrari comparison used this distinction: the first car retained its original material route, while the second car received separate material copies so its shader could be changed without changing the first car.

8. Import failures have recognizable signatures

Visual symptomFirst layer to inspect
Car is exploded or incompleteBlender visibility, parentage, export selection, and hierarchy
Car is white or untexturedTexture files, texture search, material Base Map, and external paths
Dark body artifactsNormal Map and damage texture assignment
Tire lettering is invertedLeft/right material route, UV orientation, or material texture transform
Two cars change togetherShared external material references
Too many AnimationClipsExported action list and “all actions” baking

Do not solve a symptom at a later layer until the earlier layer has been checked. A white car is not fixed by changing the shader if the Base Map is missing. A shared shader change is not fixed by changing lighting if both cars still use one material asset.

9. Model prefab versus production prefab

Dragging an FBX with a mesh into the Scene creates a model prefab instance. That makes the hierarchy easy to place, but it does not automatically make the asset production-ready.

A learning instance is useful for:

  • checking imported geometry and hierarchy;
  • testing material routing;
  • comparing shaders and texture transforms;
  • checking animation subassets;
  • capturing evidence.

A production prefab should be created only after the import contract is stable. It must have an intentional root, correct car/driver boundaries, controlled material references, required components, and a documented ownership of future overrides.

The Ferrari was intentionally kept as a learning reference. Its 188 renderers, 74 textures, fragmented material structure, decal errors, and duplicated animation clips make it useful for diagnosis but expensive as a direct production prefab.

10. Controlled exercise

  1. Use Ferrari643_Learning_Complete.fbx as the imported model source.
  2. Select the FBX in the Project window and record its Model, Animation, and Materials settings.
  3. Expand the FBX subassets and identify one mesh, one material, one texture, and one AnimationClip.
  4. Choose one renderer and trace its material slot to the material and Base Map.
  5. Place one temporary instance in AssetLearningLab.unity.
  6. Create an isolated material route for a second test instance; do not reuse the first car's material assets.
  7. Change only the second instance's shader to Simple Lit.
  8. Confirm that the first instance remains unchanged.
  9. Record whether the result is still a learning instance or is ready for a production prefab.
Expected reasoning

The important result is not merely “the second car looks different.” The result must show that the second car reaches a different material asset through a different routing path. If both cars change together, the material is shared. If the fields are grey, the selected material is probably embedded. If the model is white, inspect texture resolution before changing the shader.
