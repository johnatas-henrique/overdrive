Overdrive Asset Production · Lesson 6

Blender asset preparation and export validation

2026-08-07 · Mission: MISSION.md · ~50 min

The question this lesson answers

How do you know that a Blender scene is actually ready to export, instead of merely containing objects with plausible names?

An export is valid only when the visible result, object relationships, variants, and animation dependencies have all been checked.

This lesson exists because the first Ferrari export exposed several hidden problems: important body objects were hidden with per-view-layer state, the car was exported without every intended variant, and enabling all animation actions produced a large set of duplicated Unity clips.

1. Protect the source before inspecting it

Do not use the original Blender file as the working test file.

  1. Open the original .blend file.
  2. Use File → Save As.
  3. Create a copy with a diagnostic name, for example:
asr_ferrari_643_export-validation.blend

The original file remains the source of truth. The validation copy is allowed to contain temporary visibility changes, preview cameras, selection changes, and export tests.

2. Understand the four visibility states

Blender visibility is not one single switch. An object can appear available in the Outliner and still be absent from the active viewport or view layer.

State to inspectWhat it controlsWhy it matters
Object viewport visibilityWhether the object is visible in the current 3D ViewA hidden body part can make the export look exploded
Render visibilityWhether the object appears in a renderA preview render can falsely look incomplete
Collection visibilityWhether an entire collection is availableA disabled collection can hide many valid objects
View Layer statePer-view-layer overrides such as hidden objectsThe same file can look different in different view layers

Practical visibility check

  1. Open the Outliner.
  2. Confirm that the relevant car collection is enabled.
  3. Check the eye icon for the car body, cockpit, cover, airscope, and wheels.
  4. Check the camera icon if you are using a render as the preview.
  5. Press Alt+H in the 3D View to reveal objects hidden in the current view.
  6. Switch through every relevant entry in the View Layer selector and repeat the check.

Do not conclude that an object is visible because its name exists in the Outliner. The effective state is the state seen by the active View Layer and viewport.

3. Prove that the car is visually complete

A complete hierarchy is not the same as a complete car. The validation question is visual:

Can I see a complete, assembled car from every required view?

Use the Material Preview or Rendered shading mode. Check at least these views:

  1. front three-quarter;
  2. rear three-quarter;
  3. left side;
  4. right side;
  5. top;
  6. underside and wheel area.

For each view, look for:

  • missing main body panels;
  • missing cockpit or engine cover;
  • wheels detached from the car;
  • parts floating far from the chassis;
  • duplicate parts occupying the same space;
  • unexpected helper geometry or validation objects;
  • visible driver parts that should belong to a separate export.

Save screenshots of the six views. These are visual evidence, not decoration.

4. Verify variants instead of trusting their names

The Ferrari contains variant objects such as CINTURE_ON and CINTURE_OFF. The name alone does not prove whether an object is an alternate, a helper, or a required production state.

For each variant:

  1. locate the object or collection in the Outliner;
  2. make it visible while hiding the competing variant;
  3. render or inspect the complete car;
  4. confirm that it changes the intended visual element;
  5. record whether Unity must receive both variants or only one.

For Overdrive's driver-belt case, both meaningful states must remain available for Unity-side control. Do not delete or omit CINTURE_OFF merely because the name looks like a discardable alternate.

5. Verify parentage and asset boundaries

Use the Outliner indentation to check which objects are children of which parents. A wheel should remain attached to the correct wheel assembly, and a driver should not accidentally become part of the car mesh export.

The intended boundary is:

Car export
  body, cockpit, wheels, steering wheel, dashboard, suspension

Driver export
  driver mesh, armature, clothing, gloves, helmet

Inspect the parent chain of important objects. If a driver mesh is parented under the car only because the source scene was convenient, that is not sufficient reason to export them as one production asset.

6. Inspect animation actions before exporting

Open the Dope Sheet and switch it to Action Editor. Use the action selector to inspect the available actions one at a time.

Classify each action:

Action categoryMeaningExport treatment
Production actionNeeded by the car or driver at runtimeKeep and export deliberately
Validation actionTemporary pose or alignment checkUse during inspection, then remove
Duplicate or generated actionCreated by the exporter or source pipelineDo not export without a reason
Unrelated actionBelongs to another object or testExclude from this asset export

Actions with names beginning VAL_ were used in the Ferrari inspection as validation controls. They must not remain assigned to production bones after the validation step, because they can create misleading poses or clipping at non-neutral frames.

Why “all actions” is dangerous

The learning export used bake_anim_use_all_actions=True. Unity imported 154 AnimationClip subassets from 10 actions and 283 objects. That result proves that animation baking occurred, but it is not a clean production animation library.

Before export, decide explicitly:

Which object is animated?
Which action is required?
Which frame range is required?
Which validation actions must be excluded?

Do not enable “all actions” simply because it is available in the exporter.

7. Export car and driver separately

Use separate export selections:

  1. select the complete car hierarchy;
  2. export the car to a car-specific FBX;
  3. select the driver hierarchy;
  4. export the driver to a driver-specific FBX.

Before each export, verify the selection in the Outliner and record the export filename. Do not rely on the active object alone when the asset contains hundreds of objects.

Use a naming pattern that makes the boundary obvious:

Ferrari643_Learning_Car_Complete.fbx
Ferrari643_Learning_Driver.fbx

Keep the texture workflow explicit. If textures are not embedded, copy or import the referenced texture files into the Unity asset folder and verify that every material resolves to the intended image.

8. Validate the imported FBX in Unity

  1. Wait for Unity to finish importing.
  2. Select the FBX in the Project window.
  3. Inspect the generated hierarchy and subassets.
  4. Drag the model into AssetLearningLab.unity as a temporary reference instance.
  5. Check the same six views used in Blender.
  6. Check that textures and materials resolve.
  7. Check that the car and driver remain separate.
  8. Count the generated animation clips and compare them with the intended list.

Unity validation is not complete if the FBX imports without an error but the visual result is exploded, white, missing textures, or missing required variants.

10. Controlled exercise

  1. Open the Ferrari source copy in Blender.
  2. Check the active View Layer and reveal the car body.
  3. Capture front, rear, left, right, top, and underside views.
  4. Inspect CINTURE_ON and CINTURE_OFF as separate variants.
  5. Inspect the car and driver parent boundaries.
  6. List every action and mark it Production, Validation, Duplicate, or Unrelated.
  7. Export car and driver as separate learning FBXs.
  8. Import both into Unity and compare the result with the Blender screenshots.
Expected reasoning

A successful export is not defined by the presence of an FBX file. It is defined by a matching visual result in Blender and Unity, a verified object boundary, deliberately selected variants, and an intentional animation list. If any of these is unknown, the asset is still in validation.

Decision rule

inspect effective state
  → preview every required view
  → classify variants and actions
  → export the smallest intentional scope
  → reopen in Unity
  → compare against baseline
  → accept only with evidence
