## Context

**GDD**: `design/gdd/content-pipeline.md`
**Requirement**: `TR-content-003`
*(Requirement text lives in `docs/architecture/tr-registry.yaml` — read fresh at review time)*

**ADR Governing Implementation**: ADR-0003: Content Pipeline and Addressables; ADR-0001: Manual Simulation Authority and Determinism Boundary
**ADR Decision Summary**: CP_ state machine (Idle → LoadingTrack → LoadingCars → Ready → Racing → Unloading → Idle + transient RaceReconfigure) maps onto SimulationState. Content emits readiness/errors (`RaceLoadReady`, `ContentLoadError`, `ContentUnloadComplete`); Simulation ACCEPTS them. Content never writes `SimulationState`. RaceReconfigure: no Addressables I/O — cache hit only.

**Engine**: Unity 6000.3.22f1 (Unity 6.3 LTS) | **Risk**: HIGH (Kernel handshake — direction must be exact)

**Engine Notes**: Simulation Kernel (stories 1-8, DONE) already emits `ContentLoadRequested` (SimulationStateMachine.cs:217) and `ContentUnloadRequested` (:371-380), and consumes Content readiness/errors via `OnRaceLoadReady` (:225-245) and `OnContentLoadError` (:251-259). **Content EMITS readiness; Simulation ACCEPTS it — the reverse would be a defect.**

**Performance disposition**: The CP_ state machine is orchestration code — it runs only on discrete events (race select, load completion, unload request), never per-frame, and performs no Addressables I/O itself (load orchestration is Story 003). Zero gameplay-loop impact; no budget required beyond the orchestration latency budget measured at the assembly gate (TD-026).

**Control Manifest Rules (Foundation layer)**:
- Required: CP_ state machine: CP_Idle → CP_LoadingTrack → CP_LoadingCars → CP_Ready → CP_Racing → CP_Unloading → CP_Idle (7-state base lifecycle) + transient `CP_RaceReconfigure` — source: ADR-0003
- Required: RaceReconfigure performs NO Addressables load/unload (cache hit only); `RaceReconfigureStart` is a one-way event — source: ADR-0003
- Required: `RaceLoadReady(RaceMode, GridAssignment)` emitted only when ALL assets are fully loaded — track instance instantiated + car prefab ASSETS loaded (car GameObject spawning is Vehicle Physics/Grid & Start, architecture.yaml:224) — source: ADR-0003

*From GDD `design/gdd/content-pipeline.md`, scoped to this story:*

- [ ] **AC-SM1**: Given app initializes, When Content Pipeline starts, Then initial state is Idle with only the Shared resource reported loaded (via the injected resource-state snapshot — real Shared loading is Story 005).
- [ ] **AC-SM2**: Given Idle state, When no race selected, Then the injected resource-state snapshot reports zero race resources (no car/track bundles).
- [ ] **AC-SM3**: Given a loaded state (CP_Ready, CP_Racing, or CP_RaceReconfigure) and the Kernel emits `ContentUnloadRequested` (payload `ContentUnloadRequest`), When Content receives it, Then state transitions to Unloading and Content does NOT emit `ContentUnloadComplete` prematurely (only after the cleanup seam reports complete). In CP_Idle a `ContentUnloadRequested` is a no-op (nothing loaded — stays Idle). *(Simulation's own Results-state retention is verified by Simulation integration tests — out of this story's seams.)*
- [ ] **AC-SM4**: Given Loading Track or Loading Cars state, When the load seam reports failure (`ReportLoadError(ContentErrorType, reason)`), Then the observable ordering is: seam failure → `BeginCleanup()` called → state reaches CP_Unloading → `ReportCleanupComplete()` received → `ContentLoadError` emitted to the Kernel → CP_Idle (**cleanup-before-error — Story 005 gate F9 / Kernel :251-259**). **The SM exposes NO cancel surface: the request inputs (`ContentUnloadRequested`, `ContentLoadRequested`) are no-ops while Loading* — no transition, no seam call, no `ContentLoadError`, no completion loss (this is the testable form of "Cancel/Back does not cancel"; the UI Cancel/Back flow itself is Story 006). `Report*Loaded`/`ReportCarDegraded` continue to ADVANCE the load (AC-LO5) — they are progress inputs, not cancel surfaces.** *(Actual handle release is Story 004 — this story asserts the seam-call order, not the release.)*
- [ ] **AC-SM5**: CP_Ready is TRANSITIONAL — Given the snapshot is complete, When the SM enters CP_Ready, Then it calls `IReadinessForwarder.Forward` IMMEDIATELY and transitions to CP_Racing in the same operation: Ready is never a resting state (it exists only between the AC-LO5 completion and the publication — the "no publication occurs" case is unreachable by design; the countdown trigger is Kernel-owned, out of scope).
- [ ] **AC-LO4**: Given Idle state, When the Kernel emits `ContentLoadRequested`, Then the SM queries the injected selection source EXACTLY ONCE, stores the returned `RaceContentSelection` (TrackId + TeamIds) AND the request payload (RaceMode + GridAssignment), transitions to Loading Track, and calls `RequestTrackLoad(trackId)` on the load seam. An ignored request (busy state) performs ZERO selection-source queries. *(Player/RSM selection is out of this story — the selection source is the injectable port; the unit test drives a fake source.)*
- [ ] **AC-LO5**: Given Loading Cars state, When synthetic completion inputs arrive (`ReportTrackLoaded` + per-car `ReportCarLoaded(teamId)` or `ReportCarDegraded(teamId)` — a degraded car is a COMPLETED slot, placeholder fills the grid per GDD:144 — each updates the resource snapshot; aggregation tested WITHOUT real Addressables), Then the snapshot reports the full expected set (1 track + 16 car slots, loaded OR degraded) and state transitions THROUGH transitional Ready to CP_Racing (the LO5 completion triggers the immediate Forward per AC-SM5/LO6 — the observable terminal state is CP_Racing). Fewer than 16 completed slots → stays Loading Cars.
- [ ] **AC-LO6** (corrected direction): Given CP_Ready state (transitional) and the resource snapshot reporting all race resources loaded, When the SM calls `IReadinessForwarder.Forward(mode, grid)` with the EXACT stored payload (the RaceMode + GridAssignment captured from `ContentLoadRequested` — never invented; the SM is the caller, the forwarder is the injectable port), Then the SM transitions Ready → CP_Racing IMMEDIATELY after the forward returns (publication success = no throw — the SM does not wait for a Kernel acknowledge, `OnRaceLoadReady` is void), `RaceLoadReady` was emitted once, and the SM `HandoffValid` flag is SET (valid from this point; the concrete `IRaceContentRuntime.IsValid` is a projection of this flag — Story 003 mounts it). Content remains loaded while the Kernel runs Qualifying/Countdown/Racing. *(Simulation's own acceptance transition is verified by Simulation integration tests.)*
- [ ] **AC-LO7**: Given the Kernel emits `ContentUnloadRequested`, When Content receives it, Then Content transitions to Unloading without requiring the Kernel to enter Idle first. *(No Simulation-state assertion — kernel transitions are out of scope.)*
- [ ] **AC-LO8**: Given Unloading state, When the cleanup seam reports cleanup complete, Then Content emits `ContentUnloadComplete`; Content emits it ONLY after that signal, and the SM `HandoffValid` flag is CLEARED (invalid from this point — consumers must not retain it). *(Actual handle/instance release is Story 004; the Kernel's Idle entry after the signal is Simulation-owned.)*
- [ ] **RaceReconfigure** (ADR-0003:72-74, :155-172, GDD:146): Given Content in CP_Racing and the Kernel emits `ContentLoadRequested` (mode Race, grid), When the SM's fresh selection-source query returns a selection EQUAL to the stored one (trackId + set equality of sorted TeamIds — the `Identity()` rule), Then Content transitions CP_Racing → CP_RaceReconfigure → CP_Ready → re-emits `RaceLoadReady(RaceMode.Race, gridAssignment)` using the request's grid (the re-emit is the SAME publication that drives Ready → CP_Racing per AC-LO6 — the observable terminal state after the re-emit is CP_Racing), emits `RaceReconfigureStart` (one-way event, once), re-sets the SM `HandoffValid` flag (re-set after the re-emit — the concrete TrackInstance/CarReferences payload is Story 003's, the SM only toggles the validity flag), and performs ZERO Addressables I/O — verified by the spy on `IContentLoadSeam` (zero `Request*`/`Report*` calls during reconfiguration). **This path ALSO covers the Kernel's physics/racing RETRY (RequestRetry, SimulationStateMachine.cs:352-357 — racing failure reload): the retry is a lightweight race restart with no asset unload/reload (ADR-0003:53, :198), so a same-selection retry follows the reconfigure cache-hit path, not a full load.**
- [ ] **NextRace** (GDD:147): Given Content in CP_Racing and the Kernel emits `ContentLoadRequested` (mode Race, grid) for a NEXT race, When the fresh selection-source query returns a selection DIFFERENT from the stored one, Then Content transitions CP_Racing → CP_LoadingTrack (NOT RaceReconfigure — the GDD next-race rule); the previous SM `HandoffValid` flag is CLEARED (the old runtime must not be retained); no `ContentUnloadComplete` is emitted on this path (the previous race is unloaded internally by the next LoadRace — Story 003/004, not asserted here).
- [ ] **AC-EC6** (double-click): Given Content is in a busy state (CP_LoadingTrack, CP_LoadingCars, or the transitional CP_Ready instant), When a second `ContentLoadRequested` arrives, Then the second request is ignored: no state change, no load-seam call, ZERO selection-source queries, no duplicate `RaceLoadReady`, and the first request's mode/grid is preserved. **CP_Racing is NOT busy — it processes next-race requests (NextRace AC, GDD:147).** *(Kernel also rejects repeated starts at :207-218 — Content stays idempotent.)*

## Implementation Notes

*Derived from ADR-0003 Implementation Guidelines:*

- **State machine** (ADR-0003:66-84, GDD:140-152): `CP_Idle → CP_LoadingTrack → CP_LoadingCars → CP_Ready → CP_Racing → CP_Unloading → CP_Idle`. Error path: `CP_Loading* → CP_Unloading → CP_Idle`. Reconfigure: `CP_Racing → CP_RaceReconfigure → CP_Ready → (re-emit) → CP_Racing`. Next race: `CP_Racing → CP_LoadingTrack` (GDD:147 — changed selection; unload internal to next LoadRace).
- **`CP_Error`** (ADR-0003:83): transient error-pending state before Unloading — NOT a stable state. The manifest's 7 lifecycle states + transient RaceReconfigure are canonical; CP_Error is the same state as CP_Loading* with a pending error signal (documented, not a separate stable state).
- **Readiness forwarder seam (gate-required — resolves the void-adapter ambiguity)**: the SM does NOT invoke the Kernel directly — it calls an injectable `IReadinessForwarder` (`Forward(RaceMode, GridAssignment)`) EXACTLY ONCE per accepted readiness, and ONLY from CP_Ready (the SM guards: forward is only called from CP_Ready; calls are never attempted from any other state — stale/invalid calls are structurally impossible, not silently ignored). **Trigger**: the SM calls Forward immediately upon entering CP_Ready with a complete snapshot (the AC-LO5 completion event drives it; no external trigger — the initial-load and RaceReconfigure re-emit paths both flow through CP_Ready). **Throw behavior**: `Forward()` must NOT throw (the Kernel's `OnRaceLoadReady` is a void event invocation) — a throw is a wiring defect and the SM does NOT catch it (fail-fast). The forwarder implementation (Story 003/composition) invokes `SimulationStateMachine.OnRaceLoadReady`; the SM transitions Ready → CP_Racing immediately after the forward returns (no throw = success; `OnRaceLoadReady` is void, so no acknowledge exists). Unit tests inject a fake forwarder. Registered in architecture.yaml as `content_readiness_forwarder`.
- **CP_ ↔ SimulationState mapping** (ADR-0003:76-83): CP_Idle→Idle; CP_LoadingTrack/Cars→Loading; CP_Ready→Loading (awaiting acceptance); CP_Racing→Countdown/Racing/Finished/Paused; CP_RaceReconfigure→Loading (brief, sync); CP_Unloading→Results (after ContentUnloadRequested).
- **RaceReconfigure vs NextRace decision** (GDD:146-147): BOTH are triggered by `ContentLoadRequested` while CP_Racing. The SM makes ONE fresh selection-source query per accepted request and compares against the stored selection: EQUAL → RaceReconfigure (zero I/O, cache hit — ALSO covers the Kernel's racing retry, RequestRetry:352-357, per ADR-0003:53/198 lightweight restart); DIFFERENT → CP_LoadingTrack (next race — the previous race is unloaded internally by the next LoadRace, Story 003/004; no ContentUnloadComplete on this path). The selection-source query is EXACTLY ONCE for every accepted `ContentLoadRequested` in ANY state (Idle or CP_Racing).
- **Handoff validity contract (dual-path — resolves Story 003/004 contradiction)**: the SM maintains the runtime validity as an INTERNAL flag (`HandoffValid`, bool — observable state of the state machine, unit-testable without the concrete `IRaceContentRuntime`; the Story 003 implementation reads the flag when mounting the handoff). Invalidation happens at the EARLIEST of two paths: (a) UNLOAD path — `ContentUnloadComplete` emitted (architecture.yaml:224, Story 004) clears the flag; (b) NEXT-RACE path — the transition into CP_LoadingTrack clears the flag immediately (the previous runtime is superseded by the next LoadRace; NO ContentUnloadComplete is emitted because the unload is internal to the next LoadRace, GDD:147). Setting happens at every successful `RaceLoadReady` emission (initial and re-emit). Consumers (Vehicle Physics/Grid & Start) must not retain the runtime past either invalidation.
- **Readiness guarantee** (ADR-0003:159, superseded by architecture.yaml:224): Content instantiates the track instance and loads car prefab ASSETS before RaceLoadReady; car GameObject spawning is Vehicle Physics/Grid & Start — so VehiclePhysicsSystem can subscribe to collision events on tick 0.
- **Busy-input and idempotency rules (gate-required)**: `ContentLoadRequested` is a no-op in CP_Unloading (the SM is busy unloading — a new request is deferred to after Idle, GDD unload-then-load; the unit test asserts no transition and no seam call). Duplicate inbound callbacks are IDEMPOTENT: a second `ReportCleanupComplete()` after the first is ignored (ContentUnloadComplete emitted exactly once — AC-LO8), a second `ReportLoadError()` during the same error path is ignored, and repeated `ReportCarLoaded`/`ReportCarDegraded` for the same team ID are no-ops (set-semantics already dedupe the snapshot).
- **Adapter contract (gate-required — declared here)**: the handshake adapter consumes Kernel events `ContentLoadRequested` (→ CP_LoadingTrack) and `ContentUnloadRequested` (→ CP_Unloading) and emits/forwards `RaceLoadReady(mode, grid)`, `ContentLoadError`, `ContentUnloadComplete` into `SimulationStateMachine.OnRaceLoadReady` / `OnContentLoadError` / `OnContentUnloadComplete` (all confirmed present in the Kernel: SimulationStateMachine.cs:93-96, 225-258, 421-428). `OnRaceLoadReady` is void — the adapter contract is INVOCATION WITH EXACT PAYLOAD, not an acknowledge; Content's own active-state transition follows its own readiness publication.
- **Injectable seams (gate-required — declared here)**: (1) `IContentSelectionSource` — injectable port supplying the current selection as `RaceContentSelection` (readonly struct: `TrackId` + sorted `IReadOnlyList<string> TeamIds` — the canonical car identifier is the TEAM id: the AddressableKeys address is `Cars/{teamId}/CarDefinition` (Story 001 DONE); the same type/`Identity()` rule Story 003 consumes, `{TrackId}|{sorted TeamIds}`): the SM queries it EXACTLY ONCE per accepted `ContentLoadRequested` (AC-LO4), stores the result AND the request payload (RaceMode + GridAssignment), and issues the seam calls from the stored selection. Implemented by Story 003/composition (which receives the selection from the RaceSessionManager); unit tests inject a fake. (2) `IContentLoadSeam` — load orchestration port, SINGLE direction ownership: the SM calls outbound `RequestTrackLoad(string trackId)` / `RequestCarLoads(IReadOnlyList<string> teamIds)` — **BOTH ISSUED TOGETHER on load start (BeginLoad and NextRace) so the load implementation (Story 003) can start all 17 handles in parallel (TR-content-002); track-first COMPLETION still drives LoadingTrack → LoadingCars (ReportTrackLoaded), but the car REQUEST is not deferred to it; CAR COMPLETIONS ARE BUFFERED during LoadingTrack (17-parallel — a car may finish before the track; `RecordCarCompletion` accepts LoadingTrack AND LoadingCars; readiness fires when the LAST required slot completes — possibly at ReportTrackLoaded if all cars already buffered)**; the inbound callbacks `ReportTrackLoaded(int sessionGeneration)` / `ReportCarLoaded(int sessionGeneration, string teamId)` / `ReportCarDegraded(int sessionGeneration, string teamId)` / `ReportLoadError(int sessionGeneration, ContentErrorType, string reason)` are PUBLIC METHODS OF THE SM — **SESSION FENCING: every `Report*` carries the SM's `SessionGeneration` token — the load implementation reads `ContentStateMachine.SessionGeneration` when it receives a `Request*` and returns it in every `Report*`; the SM accepts ONLY reports carrying the CURRENT token (a stale report from a previous session — e.g. a late Addressables callback — cannot abort or complete the current session; the same generation-counter pattern as story 3-3's display-confirm and the cleanup seam's generation)**. (the real load implementation, Story 003, invokes them on the SM — the same inbound-method pattern as `SimulationStateMachine.OnRaceLoadReady`) — `ContentErrorType` is the KERNEL enum `{Track, Shared, Catalog}` (SimulationContracts.cs:63-69). `ContentResourceState Snapshot { get; }` is an SM property: the SM OWNS the immutable resource-inventory value type (`bool IsSharedLoaded` + `IReadOnlyCollection<string> CompletedRaceResourceIds` — **completed** = loaded OR degraded-placeholder, GDD:144), concrete form: readonly struct backed by an internal `HashSet<string>`, the getter returns a DEFENSIVE COPY, set-semantics (duplicates impossible, unknown IDs outside the expected set are IGNORED, no ordering — readiness compares by set equality against the expected 1-track+16-slot set). The SM's INITIAL snapshot is SEEDED via constructor (composition supplies the Shared-loaded state — Story 005 loads Shared at startup before the CP starts; the unit test seeds `IsSharedLoaded=true` directly); subsequent states are driven by inbound reports. Completions (`Report*Loaded`) rebuild the snapshot. (3) `IContentCleanupSeam` — `void BeginCleanup(int cleanupId)` (called by the SM when entering CP_Unloading — delegates the real release to the Story 004 implementation; the SM GENERATES the cleanup id (monotonic, never reused, SM-owned) and the implementation echoes it back) + `ReportCleanupComplete(int cleanupId)` (consumed before the SM emits `ContentUnloadComplete` — the ONLY trigger for that emission, AC-LO8; the SM accepts ONLY the id it generated — session fencing: a stale callback from a previous session's cleanup is ignored, the same generation-counter pattern as story 3-3's display-confirm). (4) `IRaceContentRuntime` — the ARCHITECTURE-registered handoff (architecture.yaml:224): `TrackInstance`, `CarReferences` (loaded prefab assets, NOT instantiated — Vehicle Physics/Grid & Start spawn car GameObjects), `Grid`, `IsValid`. The SM does NOT type the concrete payload — it toggles handoff validity as state (valid from RaceLoadReady until ContentUnloadComplete or a next-race transition; asserted in AC-LO6 set / AC-LO8 cleared / NextRace cleared) and exposes the flag; the concrete payload types are Story 003's.
